# Логирование флоу и производительности

## Задача и карта покрытия

Нужно восстановить путь создания туду, отличить ошибку от отмены и деградации, увидеть задержку конкретного этапа и ограничить стоимость диагностики для VM. Карта составлена по текущему `origin/main`: веб и Mac WebView, нативный быстрый ввод, Telegram, очередь разбора, ИИ, календари, уведомления и администрирование. Отдельного голосового флоу в этой версии приложения уже нет; голосовое сообщение Telegram сохраняется как вложение.

Обычный медленный запрос/операция помечается от 1 с, внешнее HTTP — от 2 с. Long polling Telegram и SSE не считаются медленными пользовательскими запросами.

## Формат и связь событий

Одна строка JSON на событие, `schemaVersion:1`, UTC `at`, `service:kizuna`, `event`, `level`. Общий контекст: `flowId`, `requestId`, `userId`, `browserSessionId`, `pageId`, `surface/source`, затем ID записи и задания. Контекст очереди сохраняется в `capture_jobs.trace_json` и переживает рестарт. Старые задания без контекста получают новый flow ID и сохраняют связь через capture/job ID.

Клиентские часы сохраняются отдельно как `clientAt`; порядок внутри страницы — `pageId + seq`. Клиентский ввод не является доказательством серверного сохранения: это подтверждают `capture_queued`, `capture_job_succeeded` и HTTP-результаты. Сервер берёт actor из сессии. Клиентские UUID служат корреляцией и не дают доступа к записи.

Пример пути: `capture_focused → capture_input → capture_submit → capture_queued → capture_job_started → ai.classify → capture_job_succeeded → capture_accepted/capture_job_observed → capture_result_visible`. При асинхронной отправке accepted приходит до завершения разбора. Исправления связываются с записью по `captureId`, а имена полей показывают, что человек изменил после разбора. Повторное сохранение с тем же ключом помечается `existing`, без второй записи.

Для изучения процесса доступны время обдумывания/редактирования, число вставок и удалений, источник, прерывания, ожидание, fallback, повтор и последующие исправления. Полный смысл записи и версии разбора читаются по `captureId` из уже существующих `captures`, `interpretations`, `corrections`, `ledger_events` с проверкой прав доступа. Технические логи не создают вторую копию содержимого туду.

## Хранение и защита VM

- JSONL: `/opt/kizuna/data/logs` на VM; локально — `logs/` рядом с SQLite. Каталог `0700`, файлы `0600`, вне rsync-каталога кода и вне HTTP-статики.
- Активный `events.jsonl` и 7 архивов по 8 МиБ: суммарно не более **64 МиБ**. Ротация перед превышением размера, также раз в сутки; TTL **14 дней**. Очистка при запуске/записи и раз в минуту, включая тихий период и архивы от прежнего большего лимита.
- Очередь логгера — **1 МиБ**, событие — до **8 КиБ**. Запись асинхронная. При переполнении, ошибке записи или остатке места менее **512 МиБ** события пропускаются; `droppedEvents`, `writeFailures`, `lowDisk` видны в runtime health. Запас места проверяется по файловой системе и уменьшается на записанные байты между проверками.
- Ротация владеет только файлами `events[.N].jsonl`. Один процесс приложения владеет одним каталогом; запускать два пишущих процесса в один каталог нельзя.
- Системный stdout/stderr помещается в namespace `kizuna`: бюджет journal **64 МиБ**, файл 8 МиБ, TTL **7 дней**, резерв 512 МиБ. Runtime journal ограничен 16 МиБ. Journald удаляет архивы, поэтому его бюджет может превышаться активным файлом; это отдельное ограничение от строгого JSONL-cap. Настройки остальных служб VM не меняются. Namespace требует systemd ≥245.
- `auth_events`: 90 дней / 20 000 строк; очистка на старте, раз в час и каждые 100 записанных событий входа (между очистками возможно до 99 дополнительных строк). Поисковая диагностика: 30 дней / 10 000 строк глобально, дополнительно существующий лимит 1 000 на человека. Удаление каскадно чистит причины совпадений. На диске SQLite переиспользует освобождённые страницы; это не VACUUM.
- Исходные туду, интерпретации, исправления и фактический ledger — данные продукта; их удаление регулируется пользовательским сбросом/архивированием. Они не участвуют в ротации диагностики.

Параметры JSONL: `PAGENT_LOG_DIR`, `PAGENT_LOG_FILE_MIB` (1–16, default 8), `PAGENT_LOG_FILES` (2–16, default 8), `PAGENT_LOG_DAYS` (1–30, default 14), `PAGENT_LOG_FREE_MIB` (64–4096, default 512). Некорректные значения возвращаются к умолчаниям. При уменьшении числа архивов лишние удаляются. Сам `audit` из тестов не создаёт файлов.

Клиентская очередь — до 80 событий, пачка — до 40. Отправка каждые 6 секунд, при восстановлении сети/уходе страницы; endpoint требует вход, same-origin защиту и ограничен 120 событиями в минуту с начальным запасом 300 на пользователя. Сервер принимает только известные имена и поля. Нативный ввод собирается пачкой раз в 2 секунды, изменения ввода объединяются, очередь до 40; отправка не блокирует сохранение.

В технические логи не допускаются текст туду/заметки/обсуждения, поисковый запрос, email, IP, тело ИИ-ответа, промпт, clipboard, клавиши, DOM/скринкасты, URL календаря/бота/push, cookie, токены и значения настроек. Ошибка содержит безопасный код/класс и номера строк файлов без текста exception. Старые security/search таблицы имеют собственные права и ретеншн.

## Как читать

```sh
# Общая сводка, проблемы, среднее/p95/max по маршрутам и операциям.
npm run logs:report -- --directory /opt/kizuna/data/logs --since 2026-10-04T00:00:00Z

# Путь создания и последующие действия по записи (последние 500 событий).
npm run logs:report -- --directory /opt/kizuna/data/logs --capture-id UUID --timeline
npm run logs:report -- --directory /opt/kizuna/data/logs --flow-id UUID --timeline
npm run logs:report -- --directory /opt/kizuna/data/logs --user-id UUID --timeline

# Все сохранённые строки выбранного флоу для локального анализа.
npm run logs:report -- --directory /opt/kizuna/data/logs --flow-id UUID --events
npm run logs:report -- --directory /opt/kizuna/data/logs --errors
journalctl --namespace=kizuna -u kizuna --since '1 hour ago'
```

CLI читает файлы потоком, держит ограниченную выборку для p95 (помечает `sampled` от 2 000 значений) и ограниченные последние проблемы/таймлайн. Воронка считает уникальные flow ID в сохранённых данных (до 10 000 на этап). Она отражает удержанный период, а не всех пользователей за всё время. Отсутствие клиентского события может означать закрытую страницу, отсутствие сети или потери телеметрии; это не равнозначно поломке сохранения.

Публичный `GET /healthz` проверяет чтение SQLite и возвращает только `status`, без данных аккаунтов. Для обнаружения полного падения VM он пригоден внешнему uptime-монитору: локальный процесс после остановки не может записать событие о собственной недоступности.

## Выкладка и проверки

`deploy.sh` устанавливает service/journald drop-in через `ops/install-observability.sh` перед обычным перезапуском. Ветка сама ничего не меняет на VM. После одобренного релиза проверить `/healthz`, `service_started`, `runtime_health`, реальную запись из каждого источника, `capture_result_visible`/`telegram_result_delivered`, фактический размер/права каталога, `journalctl --namespace=kizuna --disk-usage` и отсутствие секретов. При проблеме с namespace installer завершится до перезапуска приложения.

Автоматические проверки: изоляция параллельных контекстов; корреляция после рестарта; приватность; неработающий sink; размеры/TTL/рестарт ротации; очередь/низкое место/восстановление; очистка технических таблиц; клиентский реальный путь до результата, сетевой отказ и повтор, ошибки JS и offline flood; общий unit-набор и Mac build. Продуктовые API сохраняют ответы и идемпотентность.

Проверено локально 2026-10-04:

- `npm test`: **872/872**, из них 9 новых проверок инфраструктуры логирования. Установщик проверен с подменёнными командами: systemd 244 отвергается до изменений, 252 устанавливает только конфигурацию Kizuna.
- `npx playwright test tests/observability.spec.js tests/startup-load.spec.js tests/security-auth.spec.js`: **6/6**, включая вход. Первые два сценария телеметрии используют настоящий endpoint; тест переполнения клиентской очереди подменяет только его ответ, а серверная авторизация/квота проверены в unit-наборе.
- В реальном JSONL после браузерного прогона восстановлена общая цепочка `capture_input / capture_submit / capture_queued / ai.classify / capture_job_succeeded / capture_result_visible`; приватный тестовый текст и ключ модели отсутствуют. `logs:report` прочитал эти файлы. Отдельно проверен запуск процесса и SIGTERM: exit 0, последние события `service_stopping / service_stopped` сохранены.
- `bash desktop/macos/build.sh`: сборка и проверка подписи прошли. `bash desktop/macos/Tests/test-capture.sh`: проверки нативной панели и WebKit-моста прошли. Работа телеметрии на установленном Mac-клиенте после обновления ещё требует smoke.
- `git diff --check`, синтаксис JavaScript и shell: без ошибок.

Широкий браузерный набор целиком не зелёный. Все 10 падений старых сценариев `app.spec.js` / `board.spec.js` повторены в отдельном чистом checkout **467cf56** (`origin/main` на начало работы): отсутствующая подсказка ввода в разных OS-профилях, сценарий листа ввода, morning brief, просроченный чип и видимость подзадач на доске. Изменения логирования не исправляют эти независимые ожидания. Новые браузерные сценарии проходят.

Ветка не выложена: installer не запускался на VM, namespace journald и реальные интеграции после релиза нужно проверить отдельно. Внешний uptime-монитор пока не настроен.

Параметры journal namespace и правила удаления активных/архивных файлов сверены с [документацией systemd](https://www.freedesktop.org/software/systemd/man/252/journald.conf.html).
